# Отчёт по проекту: Beauty Routine Advisor

## Введение

**Beauty Routine Advisor** — AI-консультант по уходу за кожей на основе RAG-архитектуры (Retrieval-Augmented Generation). Система отвечает на вопросы пользователей об уходе за кожей, опираясь на внутреннюю базу знаний, а не только на параметрические знания языковой модели.

**Прикладная задача:** задача поиска и генерации — по текстовому запросу пользователя найти релевантные фрагменты базы знаний и сформулировать персонализированный совет с указанием источников.

**Пользователь и сценарий:** человек, интересующийся уходом за кожей. Вводит вопрос в чат («Как ухаживать за жирной кожей?»), получает структурированный ответ с рекомендациями и ссылками на разделы базы знаний.

**Цель проекта:** разработать и развернуть воспроизводимый RAG-сервис с чистой архитектурой, поддержкой нескольких LLM-провайдеров и достаточным качеством retrieval.

**Задачи:**
1. Собрать и структурировать базу знаний по уходу за кожей (58 Markdown-документов).
2. Реализовать пайплайн индексации: парсинг → чанкирование → векторизация → FAISS-индекс.
3. Разработать RAG-сервис с пост-фильтрацией по типу кожи и поддержкой нескольких LLM-провайдеров.
4. Упаковать сервис в Docker, обеспечить логирование и эндпоинт `/api/health`.
5. Провести EDA базы знаний и оценить качество retrieval.

## 1. Постановка задачи и анализ данных

### 1.1 Постановка задачи

**Тип задачи:** семантический поиск + условная генерация текста (RAG).

**Входные данные:**
- Текстовый запрос пользователя (строка произвольной длины).
- Опциональная история диалога (список пар «вопрос—ответ»).

**Выход модели:**
- Текстовый ответ с рекомендациями по уходу за кожей.
- Список источников (имя файла + раздел базы знаний), на которых основан ответ.

**Ограничения:**
- Латентность: ответ должен возвращаться за разумное время (timeout LLM = 30 с).
- Качество retrieval: система должна находить релевантные чанки, а не случайные.
- Безопасность: секреты (API-ключи) не должны попадать в репозиторий.

**Целевые метрики retrieval:**
- **Hit@K** — доля запросов, для которых хотя бы один из топ-K результатов является релевантным. Выбрана как основная, так как для чата важно «попасть» в нужную тему.
- **Recall@K** — полнота: доля всех релевантных документов, оказавшихся в топ-K. Показывает, не теряем ли мы важный контент.
- **MRR@K** (Mean Reciprocal Rank) — среднее обратное значение позиции первого релевантного результата. Показывает, насколько высоко стоит первый правильный ответ.

### 1.2 Источник и описание данных

**Источник:** самостоятельно составленная база знаний из 58 Markdown-документов по уходу за кожей. Документы написаны на русском языке и структурированы по темам.

**Структура базы знаний:**

| Папка | Тема | Документов |
|---|---|---|
| `01_nutrition_and_diets` | Питание и диеты | ~10 |
| `02_skincare_by_type` | Уход по типу кожи | ~15 |
| `03_ingredients` | Косметические ингредиенты | ~15 |
| `04_routines` | Уходовые рутины | ~10 |
| `05_concerns` | Проблемы кожи | ~8 |

Каждый Markdown-файл содержит YAML frontmatter с метаданными:
```yaml
---
title: Уход за жирной кожей
category: skincare_by_type
skin_type: oily
skin_concern: acne
tags: [oily-skin, acne, sebum]
---
```

Ключевые признаки документа: `title`, `category`, `skin_type`, `tags`, `h2_sections` (число секций), `word_count`.

**Демо-выборка:** `app/knowledge_base/skincare_kb/`

### 1.3 Разведочный анализ данных

EDA проводился в ноутбуке `app/notebooks/01_eda_knowledge_base.ipynb`.

**Ключевые наблюдения:**

- **Всего документов:** 58
- **Покрытие YAML-шапок:** 100% — все документы имеют корректные метаданные и будут проиндексированы.
- **Средняя длина документа:** ~185–196 слов (по непустым документам).
- **Среднее число h2-секций:** 1–2 на документ — каждый документ содержит несколько смысловых разделов, что обеспечивает гранулярное чанкирование.

**Распределение по типу кожи:** документы покрывают основные типы (`oily`, `dry`, `combination`, `normal`, `все типы`), что обеспечивает пост-фильтрацию в `RAGService.search()` по параметру `skin_type`.

**Шаги предобработки в пайплайне индексации** (`app/notebooks/02_data_pipeline.ipynb`, `app/init_kb.py`):
1. Загрузка Markdown-файлов с парсингом YAML frontmatter через `python-frontmatter`.
2. Семантическое чанкирование по заголовкам `#`, `##`, `###` — `MarkdownHeaderTextSplitter`.
3. Дополнительное дробление длинных секций — `RecursiveCharacterTextSplitter`.
4. Векторизация чанков моделью `ai-forever/FRIDA` (русскоязычная модель эмбеддингов).
5. Построение FAISS-индекса с косинусным расстоянием → сохранение в `app/embeddings_db/`.

## 2. Модели и эксперименты

### 2.1 Базовые модели

В качестве baseline выступает **TF-IDF поиск** — классический информационный поиск без нейронных эмбеддингов. Модель вычисляет TF-IDF векторы для всех чанков базы знаний и ищет ближайшие по косинусному расстоянию к запросу.

Baseline оценивался на ручном тест-сете из 20 запросов с известными релевантными документами.

| Модель | Hit@3 | Recall@3 | MRR@3 |
|---|---|---|---|
| TF-IDF (baseline) | 0.60 | 0.45 | 0.52 |

**Наблюдение:** TF-IDF справляется с точными совпадениями ключевых слов, но не улавливает семантику. Запросы вида «что делать с блестящей кожей» не находят документы про «себорею» и «жирный тип».

### 2.2 Улучшенные модели и эксперименты

**Улучшение 1: Семантические эмбеддинги (`ai-forever/FRIDA`)**

Замена TF-IDF на нейронные эмбеддинги модели `ai-forever/FRIDA` (русскоязычная модель от SberAI, обученная на инструктивных задачах). Векторы нормализуются (`normalize_embeddings=True`) и индексируются в FAISS.

Что дало:
- Семантическое понимание запроса — синонимы и перефразирования находят правильные документы.
- Обработка разговорного стиля запросов («у меня шелушится кожа» → документы про сухой тип).

**Улучшение 2: Пост-фильтрация по `skin_type`**

При наличии поля `skin_type` в запросе RAGService берёт `k*3` результатов и фильтрует по метаданным чанков (`meta.get("skin_type")`). Это повышает точность при конкретных запросах типа «уход для жирной кожи».

**Улучшение 3: Fetch-k расширение**

При активной фильтрации `fetch_k = k * 3`, чтобы после отсева по типу кожи оставалось достаточно релевантных чанков. Без этого при строгой фильтрации финальный список мог быть пустым.

### 2.3 Экспериментальный протокол и сравнение моделей

**Разбивка:** ручной тест-сет из 20 запросов, равномерно покрывающих все категории базы знаний. Фиксированный seed не требуется (детерминированные модели). Метрики считались при K=3 (значение `TOP_K_RESULTS` в продакшн-конфиге).

**Таблица 2.1 — Сравнение конфигураций retrieval**

| Модель / конфигурация | Краткое описание | Hit@3 | Recall@3 | MRR@3 | Комментарий |
|---|---|---|---|---|---|
| TF-IDF baseline | BM25-подобный поиск по токенам | 0.60 | 0.45 | 0.52 | Стартовая точка |
| FRIDA, без фильтрации | Семантические эмбеддинги, K=3 | 0.85 | 0.72 | 0.78 | +25% к Hit@3 |
| FRIDA + фильтрация skin_type | Финальная конфигурация, fetch_k=9 | 0.90 | 0.75 | 0.82 | Лучший результат |

### 2.4 Выбор финальной модели

Финальная конфигурация — **FRIDA + пост-фильтрация по skin_type** (строка 3 Таблицы 2.1).

**Обоснование:**
- Hit@3 = 0.90 против 0.60 у baseline — существенный прирост качества.
- Пост-фильтрация повышает точность для конкретных запросов с типом кожи без ухудшения общего качества.
- `ai-forever/FRIDA` — русскоязычная модель, обученная именно на инструктивных задачах (search_document / search_query), что соответствует нашему usecase.
- Модель работает на CPU без GPU (device=cpu), что важно для простого развёртывания.

**Trade-off:** более крупные модели (например, `text-embedding-3-large` от OpenAI) могут давать лучшее качество, но требуют платного API и сетевых запросов при каждом поиске. FRIDA работает локально, что обеспечивает независимость от внешних сервисов в части retrieval.

## 3. Архитектура решения и сервис

### 3.1 Архитектура пайплайна

```
Пользователь
    │
    ▼ POST /api/chat {"message": "..."}
Flask app (app/app.py)
    │
    ▼
LLMService.generate_response()
    │
    ├──► RAGService.search(query, skin_type)
    │        │
    │        ├── HuggingFaceEmbeddings (ai-forever/FRIDA)
    │        │   └── Векторизация запроса
    │        │
    │        ├── FAISS.similarity_search_with_score(query, k=9)
    │        │
    │        └── Пост-фильтрация по skin_type → топ-3 чанка
    │
    ├──► Формирование промпта: system + context + history + user_message
    │
    └──► LLM Provider (GigaChat / OpenRouter / LM Studio)
             │
             ▼
         Ответ + sources → JSON-ответ пользователю
```

### 3.2 API и эндпоинты

**`GET /api/health`** — проверка работоспособности.

```json
{
  "status": "ok",
  "message": "SkinCare Advisor API is running",
  "timestamp": "2026-06-13T18:00:00",
  "version": "0.1.0"
}
```

**`POST /api/chat`** — основной эндпоинт.

Запрос:
```json
{
  "message": "У меня жирная кожа и акне, что делать?",
  "conversation_history": []
}
```

Ответ:
```json
{
  "response": "## Уход за жирной кожей\n\n...",
  "sources": [
    "02_oily_skin.md › Утренний уход",
    "01_acne_and_post_acne.md › Базовые рекомендации"
  ]
}
```

Статус-коды: `200` (успех), `400` (невалидный запрос), `500` (внутренняя ошибка).

### 3.3 Технологический стек и контейнеризация

| Слой | Технология |
|---|---|
| Backend | Flask 3.x + Flask-CORS |
| RAG | LangChain + FAISS (`langchain-community`) |
| Embeddings | `ai-forever/FRIDA` через `langchain-huggingface` |
| LLM | GigaChat / OpenRouter (mistral, gemma) / LM Studio |
| Тесты | pytest + pytest-cov |
| Качество кода | flake8 + black |
| Документация | Sphinx + autodoc |
| Пакетный менеджер | uv |

**Сборка и запуск:**

```bash
# С Docker:
docker build -t skincare-advisor .
docker run -p 8080:8080 --env-file app/.env skincare-advisor

# Без Docker:
make install
make init-kb   # индексация knowledge base
make run       # http://localhost:8080
```

## 4. Наблюдаемость, конфигурация и безопасность

### 4.1 Логирование и наблюдаемость

Логирование настроено через `app/utils/logger.py` с форматом:
```
%(asctime)s - %(name)s - %(levelname)s - %(message)s
```

Что логируется:
- Каждый входящий запрос к `/api/chat` с первыми 50 символами сообщения.
- Количество найденных RAG-чанков для каждого запроса (`debug`-уровень).
- Все исключения в обработчиках маршрутов (`error`-уровень).
- Запуск приложения с URL и версией.

Пример лога:
```
2026-06-13 18:00:03 - app - INFO - 📩 Получено сообщение: У меня жирная кожа...
2026-06-13 18:00:03 - services.rag_service - DEBUG - RAG: 3 чанков для 'У меня жирная кожа'
2026-06-13 18:00:07 - app - INFO - 🚀 Запуск SkinCare Advisor API
```

Эндпоинт `/api/health` возвращает статус, timestamp и версию — достаточно для базового мониторинга.

### 4.2 Конфигурация

Все параметры вынесены в `app/config.py` и переопределяются через `app/.env`:

| Параметр | Дефолт | Описание |
|---|---|---|
| `LLM_PROVIDER` | `gigachat` | Активный LLM-провайдер |
| `EMBEDDING_MODEL` | `ai-forever/FRIDA` | Модель эмбеддингов |
| `TOP_K_RESULTS` | `3` | Количество RAG-чанков |
| `PORT` | `8080` | Порт сервиса |
| `DEBUG` | `True` | Режим отладки |

Переключение провайдера — только через `.env`, без изменения кода.

### 4.3 Работа с секретами и данными

- `app/.env` добавлен в `.gitignore` — реальные ключи не попадают в репозиторий.
- В репозитории хранится только `app/.env.example` с пустыми значениями.
- API-ключи (`GIGACHAT_CREDENTIALS`, `OPENROUTER_API_KEY`) не логируются.
- В коде нет хардкоженных токенов или паролей.

**Текущие ограничения:**
- База знаний покрывает не все темы (например, мало документов о декоративной косметике).

**Направления дальнейшей работы:**
- Гибридный поиск: BM25 + FAISS для лучшего покрытия точных запросов.
- Расширение базы знаний, добавление мультимодальности (анализ фото кожи).

**Сценарий демонстрации на защите:**

4. Показать `curl http://localhost:8080/api/health` → `{"status": "ok", ...}`.
5. При необходимости сменить `LLM_PROVIDER` в `.env` и перезапустить — показать мультипровайдерность.
